# 大模型推理容量规划与插值技术复盘总结（80B / 284B / 27B 实战）

> **文档说明**：本文档完整复盘了如何基于现有离散的基准压测表数据，利用**一维线性插值**与**二维双线性插值**，科学推导出 **$80\text{B}$、$284\text{B}$、$27\text{B}$** 三款模型在目标业务场景下的单实例并发上限与机器实例规模，并汇总了推导背后的核心知识点与潜在工程风险。

---

## 一、 业务目标与现有压测数据状况

### 1.1 目标业务 SLA 要求
*   **目标输入 / 输出长度**：输入 **$3\text{k}$** / 输出 **$5\text{k}$**
*   **目标总并发数**：同时支撑 **$300$ 并发**
*   **首字时延要求（SLA）**：$\text{TTFT} \le 3\text{s}$（分别评估 **P90 严苛标准** 与 **平均值 Mean 标准**）

### 1.2 现有压测表状况（为什么要做插值推导？）
在实际工程压测中，压测表只采集了固定的离散档位（如输入 $2\text{k}$、$4\text{k}$，输出 $1\text{k}$、$4\text{k}$、$8\text{k}$），**并没有直接测试“$3\text{k}$ 输入 / $5\text{k}$ 输出”这一目标档位**。同时，三个模型的压测表完整度不同，直接决定了我们必须采用不同的插值推导策略：

1.  **$80\text{B}$ 模型（数据最全 $\to$ 采用【二维双线性插值】）**：
    *   **现有状况**：压测表同时包含 **输入（$2\text{k}$ 与 $4\text{k}$）** 和 **输出（$4\text{k}$ 与 $8\text{k}$）** 的交叉压测数据。
    *   **推导策略**：目标点 $(3\text{k}\text{ 输入}, 5\text{k}\text{ 输出})$ 刚好落在 $[2\text{k}, 4\text{k}] \times [4\text{k}, 8\text{k}]$ 的二维网格内部，因此通过**双线性插值**同时在输入、输出两个维度上按比例加权，精准定位出 $3\text{k}/5\text{k}$ 的真实 $\text{TTFT}$ 负载。
2.  **$284\text{B}$ 模型与 $27\text{B}$ 模型（受限于 $1\text{k}$ 输出 $\to$ 采用【一维线性插值】）**：
    *   **现有状况**：压测表受限于当时的测试条件，**最高仅提供了 $1\text{k}$ 输出**的数据（仅有“$2\text{k}$入/$1\text{k}$出”与“$4\text{k}$入/$1\text{k}$出”），缺失了 $4\text{k}$、$8\text{k}$ 长输出维度的数据。
    *   **推导策略**：由于缺少输出维度的阶梯数据，无法做二维插值；只能在固定 $1\text{k}$ 输出的前提下，利用 **$2\text{k}$ 与 $4\text{k}$ 输入进行单维度（一维）线性插值**，推算出 $3\text{k}$ 输入时的 $\text{TTFT}$ 表现。

## 三、 具体推导过程与数学原理拆解

### 3.1 $80\text{B}$ 模型推导过程（双线性插值法）

#### 1. 为什么要连“输出长度”一起做双线性插值？
在持续批处理（Continuous Batching）的真实压测中，虽然 $\text{TTFT}$ 表面上是处理输入（Prefill）的时间，但**输出越长（如从 $4\text{k}$ 变成 $8\text{k}$），老请求在系统里驻留的 $\text{KV Cache}$ 就越大，Decode 阶段抢占的显存带宽和算力时间片就越多**，从而拖慢新进入请求的 $\text{TTFT}$。因此，既然 $80\text{B}$ 压测表有 $4\text{k}$ 和 $8\text{k}$ 输出的数据，必须用**双线性插值**把输出长度的影响也算进去。

#### 2. 双线性插值权重计算
我们要在四个已知压测锚点 $Q_{11}(2\text{k}\text{入}, 4\text{k}\text{出})$、$Q_{21}(4\text{k}\text{入}, 4\text{k}\text{出})$、$Q_{12}(2\text{k}\text{入}, 8\text{k}\text{出})$、$Q_{22}(4\text{k}\text{入}, 8\text{k}\text{出})$ 之间，定位目标点 $P(3\text{k}\text{入}, 5\text{k}\text{出})$：
*   **第一步（算输入维度的位置比例 $u$）**：$3\text{k}$ 正好在 $2\text{k}$ 和 $4\text{k}$ 的正中间：
    $$u = \frac{3\text{k} - 2\text{k}}{4\text{k} - 2\text{k}} = 0.5$$
*   **第二步（算输出维度的位置比例 $v$）**：$5\text{k}$ 在 $4\text{k}$ 到 $8\text{k}$ 之间走了 $\frac{1}{4}$ 的路程（离 $4\text{k}$ 更近）：
    $$v = \frac{5\text{k} - 4\text{k}}{8\text{k} - 4\text{k}} = 0.25$$
*   **第三步（合成双线性插值公式）**：
    $$\text{TTFT}_{(3\text{k}, 5\text{k})} = (1-u)(1-v)Q_{11} + u(1-v)Q_{21} + (1-u)vQ_{12} + uvQ_{22}$$
    代入 $u=0.5, v=0.25$，即：**先对 $2\text{k}$ 和 $4\text{k}$ 输入取平均值（各占 $50\%$），再对 $4\text{k}$ 输出（占 $75\%$ 权重）和 $8\text{k}$ 输出（占 $25\%$ 权重）做加权求和**：
    $$\text{TTFT}_{(3\text{k}, 5\text{k})} = 0.375 \times \text{TTFT}_{(2\text{k},4\text{k})} + 0.375 \times \text{TTFT}_{(4\text{k},4\text{k})} + 0.125 \times \text{TTFT}_{(2\text{k},8\text{k})} + 0.125 \times \text{TTFT}_{(4\text{k},8\text{k})}$$

#### 3. 容量结论推导
*   **P90 SLA 约束下**：将压测表各并发档位的 P90 数据代入上述双线性插值公式，定位到当**并发数为 $60$** 时，$3\text{k}\text{入}/5\text{k}\text{出}$ 的 $\text{TTFT} \approx 2.98\text{s}$，刚好卡在 $3\text{s}$ 达标线内。
    *   绝对实例数 $= 300 \div 60 = \mathbf{5}$ **个实例**。
    *   由于 $2.98\text{s}$ 已经贴近 $3\text{s}$ 极限，考虑到线上临时高负载（突发流量峰值）场景，增加 $1$ 个冗余实例，建议扩至 **$6$ 个实例**。
*   **平均值（Mean）考核下**：将压测表的平均 $\text{TTFT}$ 代入公式，定位到当**并发数为 $100$** 时，$\text{TTFT} \approx 2.83\text{s} \le 3\text{s}$。
    *   对应实例数 $= 300 \div 100 = \mathbf{3}$ **个实例**。

### 3.2 $284\text{B}$ 模型推导过程（一维线性插值 + 前缀缓存边界分析）

由于 $284\text{B}$ 压测表最高只测了 $1\text{k}$ 输出，我们在同一并发档位下，直接对 **$2\text{k}$ 输入** 和 **$4\text{k}$ 输入** 的 $\text{TTFT}$ 做一维线性插值（因为比例 $t = \frac{3 - 2}{4 - 2} = 0.5$，本质就是取 $2\text{k}$ 与 $4\text{k}$ 耗时的算术平均值）：
$$\text{TTFT}_{3\text{k}} = 0.5 \times \text{TTFT}_{2\text{k}} + 0.5 \times \text{TTFT}_{4\text{k}}$$

#### 1. 不开前缀缓存（No Prefix Caching）
*   **P90 标准下**：通过线性插值计算发现，在 **$16$ 并发** 时，插值后的 P90 $\text{TTFT} = 2.70\text{s}$（满足 $\le 3\text{s}$；若继续调高并发则会突破 $3\text{s}$）。
    *   所需实例数 $= \lceil 300 \div 16 \rceil = \lceil 18.75 \rceil = \mathbf{19}$ **个实例**。
*   **平均值标准下**：对平均 $\text{TTFT}$ 做线性插值，$\text{TTFT} \le 3\text{s}$ 对应的单实例并发上限落在 **$28 \sim 30$ 之间**。
    *   所需实例数 $= 300 \div 30 = 10$ 至 $\lceil 300 \div 28 \rceil = 11$，即需要 **$10 \sim 11$ 个实例**。

#### 2. 开启前缀缓存（With Prefix Caching）
*   **现状与瓶颈转移**：开启前缀缓存（Prefix Caching）后，大量重复的 Prompt 前缀直接命中显存缓存，免去了沉重的 Prefill 矩阵计算，原本在 $16 \sim 30$ 并发就会卡脖子的**算力瓶颈瞬间消失**。
*   **触发系统级硬限制（`max_num_seqs` 雪崩）**：虽然算力不卡了，但推理引擎底层配置了系统最大批处理序列数限制（默认 `max_num_seqs = 64`）。这意味着单个实例最多只能同时把 $64$ 条请求放进执行队列（Running Queue）。
    *   一旦并发超过 $64$，第 $65$ 个及之后的请求根本进不了显卡计算，只能在外部等待队列（Waiting Queue）里干等。
    *   而在我们的目标场景中，输出长达 $5\text{k}$ tokens，前 $64$ 个请求要霸占槽位非常久才能吐完字退出。这会导致排队请求的首字时延（$\text{TTFT} = \text{排队时间} + \text{计算时间}$）发生**断崖式雪崩飙升**！
*   **安全容量推导**：为了严防线上流量波动撞上 $64$ 并发的排队雪崩墙，工程上必须留出约 $20\%$ 的缓冲水位，将单实例安全阈值定在 **$50$ 并发**。
    *   所需实例数 $= 300 \div 50 = \mathbf{6}$ **个实例**。

---

### 3.3 $27\text{B}$ 模型推导过程（一维线性插值）

*   **推导方法**：与 $284\text{B}$ 相同，压测表同样受限于最高 $1\text{k}$ 输出，因此固定 $1\text{k}$ 输出，按 $2\text{k}$ 与 $4\text{k}$ 输入进行一维线性插值（取权重各 $0.5$）。
*   **P90 标准下**：插值结果显示，当单实例并发在 **$10 \sim 11$ 并发** 时，P90 $\text{TTFT}$ 已经逼近 $3\text{s}$ 红线。
    *   按安全的 $10$ 并发计算，支撑 $300$ 并发所需实例数 $= 300 \div 10 = \mathbf{30}$ **个实例**。
*   **平均值标准下**：插值结果显示，当单实例并发在 **$21 \sim 23$ 并发** 时，平均 $\text{TTFT}$ 处于 $3\text{s}$ 边缘。
    *   按 $20$ 并发安全折算，支撑 $300$ 并发所需实例数 $= 300 \div 20 = \mathbf{15}$ **个实例**。

## 四、 核心知识点与潜在工程问题总结（答疑与避坑指南）

在向团队或客户汇报上述推导结论时，以下几个**核心知识点**与**潜在风险问题**需要重点说明：

### 知识点 1：用“线性插值”估算 $3\text{k}$ 输入的 $\text{TTFT}$，结果是偏激进还是偏安全？
*   **结论：偏安全（自带微小的安全冗余）**。
*   **原理解释**：大模型 Prefill 阶段的耗时由两部分组成——线性的全连接层计算 $O(N)$ 和平方级的自注意力计算 $O(N^2)$。因为有 $O(N^2)$ 的存在，“输入长度 vs $\text{TTFT}$ 耗时”的真实曲线是一条**向下凹（下凸）的加速上升曲线**。
*   当我们用一条直线连接 $2\text{k}$ 和 $4\text{k}$ 两点（做线性插值）时，这条直线在 $3\text{k}$ 处的高度，实际上略微**高于**真实下凹曲线在 $3\text{k}$ 处的值。也就是说，**如果线性插值算出来的 $\text{TTFT}$ 能控制在 $3\text{s}$ 以内，那么真实的 $3\text{k}$ 算力耗时一定比插值结果还要略快一点点**，作为工程容量规划是非常稳妥的。

### 潜在问题 1：【重点风险】$284\text{B}$ 和 $27\text{B}$ 仅用“$1\text{k}$ 输出”压测表去推导“$5\text{k}$ 输出”业务，会有什么隐患？
*   **问题本质**：$80\text{B}$ 用双线性插值把 $5\text{k}$ 输出的负载算进去了，但 $284\text{B}$ 和 $27\text{B}$ 因为压测表只有 $1\text{k}$ 输出，实际上**忽略了输出从 $1\text{k}$ 暴增到 $5\text{k}$ 带来的额外系统负担**。
*   **真实上线 $5\text{k}$ 输出时的三大潜在冲击**：
    1.  **持续批处理（Continuous Batching）的相互干扰加剧**：在压测 $1\text{k}$ 输出时，请求很快吐完字释放了；但在 $5\text{k}$ 输出时，单条请求在系统内驻留时间延长了 $5$ 倍。老请求在长达数千步的 Decode 过程中会持续占用显存带宽，并穿插在 Chunked Prefill 之间，导致新请求的实际 $\text{TTFT}$ 比 $1\text{k}$ 输出压测表里体现的要慢（可能使 $284\text{B}$ 的 $16$ 并发、$27\text{B}$ 的 $10$ 并发出现轻微超 $3\text{s}$ 的现象）。
    2.  **单请求 $\text{KV Cache}$ 显存占用翻倍**：单条请求的总上下文从 $3\text{k}+1\text{k}=4\text{k}$ 变成了 $3\text{k}+5\text{k}=8\text{k}$，显存占用直接翻倍。需要复核 $284\text{B}$ 模型在 $30 \sim 50$ 并发下，剩余显存是否足够容纳 $50 \times 8\text{k} = 400\text{k}$ tokens 的 $\text{KV Cache}$，防止发生显存不足引起的重计算（Recompute/Swap）卡顿。
    3.  **补救建议**：若条件允许，后续最好为 $284\text{B}$ 和 $27\text{B}$ 补测一组 `3k输入 / 5k输出` 的定点验证，或者在当前按 $1\text{k}$ 输出推导出的实例数基础上，预留 $10\% \sim 15\%$ 的缓冲余量。

### 潜在问题 2：为什么开启前缀缓存（Prefix Caching）后，算力明明极其充裕，并发却绝对不能超过 `max_num_seqs`（$64$）？
*   **问题机制**：很多工程师误以为“开了前缀缓存，Prefill 几乎不花时间，单实例并发就能无限往上加”。实际上，前缀缓存只省去了**计算时间**，并没有省去请求在 Decode 阶段的**槽位占用时间**。
*   **排队雪崩过程**：推理引擎调度器受到 `max_num_seqs = 64` 的硬性保护。当线上同时有 $64$ 个请求正在慢慢吐那 $5\text{k}$ 个输出字时，调度器的 $64$ 个活跃槽位全部锁死。此时哪怕第 $65$ 个请求完全命中前缀缓存（本来只需 $0.1\text{s}$ 就能出首字），它也进不了调度器，必须等前面某一个请求把 $5\text{k}$ 个字吐完腾出位置，这会导致第 $65$ 个请求的 $\text{TTFT}$ 瞬间变成几十秒！
*   **工程对策**：
    1.  像我们推导中所做的，严格将单实例路由并发限制在 **$50$ 以内**（留出安全缓冲）。
    2.  如果显存依然有大量富余，可以在引擎启动参数中尝试将 `max_num_seqs` 从默认的 $64$ 调大（如调至 $128$），观察 Decode 吐字延迟（$\text{TPOT}$）是否仍在可接受范围内，若不劣化则可进一步减少所需的实例数。

### 潜在问题 3：为什么同一个模型，按 P90 标准和按平均值（Mean）标准算出来的机器实例数差了整整一倍？
*   **数据对比**：
    *   $80\text{B}$：P90 需 $5 \sim 6$ 个实例 vs 均值需 $3$ 个实例；
    *   $284\text{B}$：P90 需 $19$ 个实例 vs 均值需 $10 \sim 11$ 个实例；
    *   $27\text{B}$：P90 需 $30$ 个实例 vs 均值需 $15$ 个实例。
*   **原因解析**：在大模型高并发压测中，当多个 $3\text{k}$ 长输入请求在同一瞬间扎堆到达时，会产生**队头阻塞（Head-of-Line Blocking）**。最倒霉的那 $10\%$ 的请求（即 P90 统计位点）必须等同批次前面的 $3\text{k}$ 请求先做完 Prefill，导致其 $\text{TTFT}$ 比平均值高出一大截。
*   **业务沟通建议**：向业务方或客户汇报时，必须明确对齐 SLA 口径——如果业务是严苛的实时交互场景（要求 $90\%$ 以上的请求绝对不能超过 $3\text{s}$），就必须按 **P90 实例数** 采购/分配算力；如果是后台异步批处理或对偶发延迟不敏感的内部应用，则可按 **均值实例数** 部署，直接节省近 $50\%$ 的硬件成本。
