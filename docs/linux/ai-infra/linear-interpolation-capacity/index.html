大模型推理容量规划与插值技术复盘总结（80B / 284B / 27B 实战）

文档说明：本文档完整复盘了如何基于现有离散的基准压测表数据，利用一维线性插值与二维双线性插值，科学推导出 80B80\text{B}80B、284B284\text{B}284B、27B27\text{B}27B 三款模型在目标业务场景下的单实例并发上限与机器实例规模，并汇总了推导背后的核心知识点与潜在工程风险。

一、 业务目标与现有压测数据状况​

1.1 目标业务 SLA 要求​

  • 目标输入 / 输出长度：输入 3k3\text{k}3k / 输出 5k5\text{k}5k
  • 目标总并发数：同时支撑 300300300 并发
  • 首字时延要求（SLA）：TTFT≤3s\text{TTFT} \le 3\text{s}TTFT≤3s（分别评估 P90 严苛标准 与 平均值 Mean 标准）

1.2 现有压测表状况（为什么要做插值推导？）​

在实际工程压测中，压测表只采集了固定的离散档位（如输入 2k2\text{k}2k、4k4\text{k}4k，输出 1k1\text{k}1k、4k4\text{k}4k、8k8\text{k}8k），并没有直接测试“3k3\text{k}3k 输入 / 5k5\text{k}5k 输出”这一目标档位。同时，三个模型的压测表完整度不同，直接决定了我们必须采用不同的插值推导策略：

  1. 80B80\text{B}80B 模型（数据最全 →\to→ 采用【二维双线性插值】）：
    • 现有状况：压测表同时包含 输入（2k2\text{k}2k 与 4k4\text{k}4k） 和 输出（4k4\text{k}4k 与 8k8\text{k}8k） 的交叉压测数据。
    • 推导策略：目标点 (3k 输入,5k 输出)(3\text{k}\text{ 输入}, 5\text{k}\text{ 输出})(3k 输入,5k 输出) 刚好落在 [2k,4k]×[4k,8k][2\text{k}, 4\text{k}] \times [4\text{k}, 8\text{k}][2k,4k]×[4k,8k] 的二维网格内部，因此通过双线性插值同时在输入、输出两个维度上按比例加权，精准定位出 3k/5k3\text{k}/5\text{k}3k/5k 的真实 TTFT\text{TTFT}TTFT 负载。
  2. 284B284\text{B}284B 模型与 27B27\text{B}27B 模型（受限于 1k1\text{k}1k 输出 →\to→ 采用【一维线性插值】）：
    • 现有状况：压测表受限于当时的测试条件，最高仅提供了 1k1\text{k}1k 输出的数据（仅有“2k2\text{k}2k入/1k1\text{k}1k出”与“4k4\text{k}4k入/1k1\text{k}1k出”），缺失了 4k4\text{k}4k、8k8\text{k}8k 长输出维度的数据。
    • 推导策略：由于缺少输出维度的阶梯数据，无法做二维插值；只能在固定 1k1\text{k}1k 输出的前提下，利用 2k2\text{k}2k 与 4k4\text{k}4k 输入进行单维度（一维）线性插值，推算出 3k3\text{k}3k 输入时的 TTFT\text{TTFT}TTFT 表现。

三、 具体推导过程与数学原理拆解​

3.1 80B80\text{B}80B 模型推导过程（双线性插值法）​

1. 为什么要连“输出长度”一起做双线性插值？​

在持续批处理（Continuous Batching）的真实压测中，虽然 TTFT\text{TTFT}TTFT 表面上是处理输入（Prefill）的时间，但输出越长（如从 4k4\text{k}4k 变成 8k8\text{k}8k），老请求在系统里驻留的 KV Cache\text{KV Cache}KV Cache 就越大，Decode 阶段抢占的显存带宽和算力时间片就越多，从而拖慢新进入请求的 TTFT\text{TTFT}TTFT。因此，既然 80B80\text{B}80B 压测表有 4k4\text{k}4k 和 8k8\text{k}8k 输出的数据，必须用双线性插值把输出长度的影响也算进去。

2. 双线性插值权重计算​

3.2 284B284\text{B}284B 模型推导过程（一维线性插值 + 前缀缓存边界分析）​

由于 284B284\text{B}284B 压测表最高只测了 1k1\text{k}1k 输出，我们在同一并发档位下，直接对 2k2\text{k}2k 输入 和 4k4\text{k}4k 输入 的 TTFT\text{TTFT}TTFT 做一维线性插值（因为比例 t=3−24−2=0.5t = \frac{3 - 2}{4 - 2} = 0.5t=4−23−2​=0.5，本质就是取 2k2\text{k}2k 与 4k4\text{k}4k 耗时的算术平均值）： TTFT3k=0.5×TTFT2k+0.5×TTFT4k\text{TTFT}_{3\text{k}} = 0.5 \times \text{TTFT}_{2\text{k}} + 0.5 \times \text{TTFT}_{4\text{k}}TTFT3k​=0.5×TTFT2k​+0.5×TTFT4k​

1. 不开前缀缓存（No Prefix Caching）​

  • P90 标准下：通过线性插值计算发现，在 161616 并发 时，插值后的 P90 TTFT=2.70s\text{TTFT} = 2.70\text{s}TTFT=2.70s（满足 ≤3s\le 3\text{s}≤3s；若继续调高并发则会突破 3s3\text{s}3s）。
    • 所需实例数 =⌈300÷16⌉=⌈18.75⌉=19= \lceil 300 \div 16 \rceil = \lceil 18.75 \rceil = \mathbf{19}=⌈300÷16⌉=⌈18.75⌉=19 个实例。
  • 平均值标准下：对平均 TTFT\text{TTFT}TTFT 做线性插值，TTFT≤3s\text{TTFT} \le 3\text{s}TTFT≤3s 对应的单实例并发上限落在 28∼3028 \sim 3028∼30 之间。
    • 所需实例数 =300÷30=10= 300 \div 30 = 10=300÷30=10 至 ⌈300÷28⌉=11\lceil 300 \div 28 \rceil = 11⌈300÷28⌉=11，即需要 10∼1110 \sim 1110∼11 个实例。

2. 开启前缀缓存（With Prefix Caching）​

  • 现状与瓶颈转移：开启前缀缓存（Prefix Caching）后，大量重复的 Prompt 前缀直接命中显存缓存，免去了沉重的 Prefill 矩阵计算，原本在 16∼3016 \sim 3016∼30 并发就会卡脖子的算力瓶颈瞬间消失。
  • 触发系统级硬限制（max_num_seqs 雪崩）：虽然算力不卡了，但推理引擎底层配置了系统最大批处理序列数限制（默认 max_num_seqs = 64）。这意味着单个实例最多只能同时把 646464 条请求放进执行队列（Running Queue）。
    • 一旦并发超过 646464，第 656565 个及之后的请求根本进不了显卡计算，只能在外部等待队列（Waiting Queue）里干等。
    • 而在我们的目标场景中，输出长达 5k5\text{k}5k tokens，前 646464 个请求要霸占槽位非常久才能吐完字退出。这会导致排队请求的首字时延（TTFT=排队时间+计算时间\text{TTFT} = \text{排队时间} + \text{计算时间}TTFT=排队时间+计算时间）发生断崖式雪崩飙升！
  • 安全容量推导：为了严防线上流量波动撞上 646464 并发的排队雪崩墙，工程上必须留出约 20%20\%20% 的缓冲水位，将单实例安全阈值定在 505050 并发。
    • 所需实例数 =300÷50=6= 300 \div 50 = \mathbf{6}=300÷50=6 个实例。

3.3 27B27\text{B}27B 模型推导过程（一维线性插值）​

  • 推导方法：与 284B284\text{B}284B 相同，压测表同样受限于最高 1k1\text{k}1k 输出，因此固定 1k1\text{k}1k 输出，按 2k2\text{k}2k 与 4k4\text{k}4k 输入进行一维线性插值（取权重各 0.50.50.5）。
  • P90 标准下：插值结果显示，当单实例并发在 10∼1110 \sim 1110∼11 并发 时，P90 TTFT\text{TTFT}TTFT 已经逼近 3s3\text{s}3s 红线。
    • 按安全的 101010 并发计算，支撑 300300300 并发所需实例数 =300÷10=30= 300 \div 10 = \mathbf{30}=300÷10=30 个实例。
  • 平均值标准下：插值结果显示，当单实例并发在 21∼2321 \sim 2321∼23 并发 时，平均 TTFT\text{TTFT}TTFT 处于 3s3\text{s}3s 边缘。
    • 按 202020 并发安全折算，支撑 300300300 并发所需实例数 =300÷20=15= 300 \div 20 = \mathbf{15}=300÷20=15 个实例。

四、 核心知识点与潜在工程问题总结（答疑与避坑指南）​

在向团队或客户汇报上述推导结论时，以下几个核心知识点与潜在风险问题需要重点说明：

知识点 1：用“线性插值”估算 3k3\text{k}3k 输入的 TTFT\text{TTFT}TTFT，结果是偏激进还是偏安全？​

  • 结论：偏安全（自带微小的安全冗余）。
  • 原理解释：大模型 Prefill 阶段的耗时由两部分组成——线性的全连接层计算 O(N)O(N)O(N) 和平方级的自注意力计算 O(N2)O(N^2)O(N2)。因为有 O(N2)O(N^2)O(N2) 的存在，“输入长度 vs TTFT\text{TTFT}TTFT 耗时”的真实曲线是一条向下凹（下凸）的加速上升曲线。
  • 当我们用一条直线连接 2k2\text{k}2k 和 4k4\text{k}4k 两点（做线性插值）时，这条直线在 3k3\text{k}3k 处的高度，实际上略微高于真实下凹曲线在 3k3\text{k}3k 处的值。也就是说，如果线性插值算出来的 TTFT\text{TTFT}TTFT 能控制在 3s3\text{s}3s 以内，那么真实的 3k3\text{k}3k 算力耗时一定比插值结果还要略快一点点，作为工程容量规划是非常稳妥的。

潜在问题 1：【重点风险】284B284\text{B}284B 和 27B27\text{B}27B 仅用“1k1\text{k}1k 输出”压测表去推导“5k5\text{k}5k 输出”业务，会有什么隐患？​

  • 问题本质：80B80\text{B}80B 用双线性插值把 5k5\text{k}5k 输出的负载算进去了，但 284B284\text{B}284B 和 27B27\text{B}27B 因为压测表只有 1k1\text{k}1k 输出，实际上忽略了输出从 1k1\text{k}1k 暴增到 5k5\text{k}5k 带来的额外系统负担。
  • 真实上线 5k5\text{k}5k 输出时的三大潜在冲击：
    1. 持续批处理（Continuous Batching）的相互干扰加剧：在压测 1k1\text{k}1k 输出时，请求很快吐完字释放了；但在 5k5\text{k}5k 输出时，单条请求在系统内驻留时间延长了 555 倍。老请求在长达数千步的 Decode 过程中会持续占用显存带宽，并穿插在 Chunked Prefill 之间，导致新请求的实际 TTFT\text{TTFT}TTFT 比 1k1\text{k}1k 输出压测表里体现的要慢（可能使 284B284\text{B}284B 的 161616 并发、27B27\text{B}27B 的 101010 并发出现轻微超 3s3\text{s}3s 的现象）。
    2. 单请求 KV Cache\text{KV Cache}KV Cache 显存占用翻倍：单条请求的总上下文从 3k+1k=4k3\text{k}+1\text{k}=4\text{k}3k+1k=4k 变成了 3k+5k=8k3\text{k}+5\text{k}=8\text{k}3k+5k=8k，显存占用直接翻倍。需要复核 284B284\text{B}284B 模型在 30∼5030 \sim 5030∼50 并发下，剩余显存是否足够容纳 50×8k=400k50 \times 8\text{k} = 400\text{k}50×8k=400k tokens 的 KV Cache\text{KV Cache}KV Cache，防止发生显存不足引起的重计算（Recompute/Swap）卡顿。
    3. 补救建议：若条件允许，后续最好为 284B284\text{B}284B 和 27B27\text{B}27B 补测一组 3k输入 / 5k输出 的定点验证，或者在当前按 1k1\text{k}1k 输出推导出的实例数基础上，预留 10%∼15%10\% \sim 15\%10%∼15% 的缓冲余量。

潜在问题 2：为什么开启前缀缓存（Prefix Caching）后，算力明明极其充裕，并发却绝对不能超过 max_num_seqs（646464）？​

  • 问题机制：很多工程师误以为“开了前缀缓存，Prefill 几乎不花时间，单实例并发就能无限往上加”。实际上，前缀缓存只省去了计算时间，并没有省去请求在 Decode 阶段的槽位占用时间。
  • 排队雪崩过程：推理引擎调度器受到 max_num_seqs = 64 的硬性保护。当线上同时有 646464 个请求正在慢慢吐那 5k5\text{k}5k 个输出字时，调度器的 646464 个活跃槽位全部锁死。此时哪怕第 656565 个请求完全命中前缀缓存（本来只需 0.1s0.1\text{s}0.1s 就能出首字），它也进不了调度器，必须等前面某一个请求把 5k5\text{k}5k 个字吐完腾出位置，这会导致第 656565 个请求的 TTFT\text{TTFT}TTFT 瞬间变成几十秒！
  • 工程对策：
    1. 像我们推导中所做的，严格将单实例路由并发限制在 505050 以内（留出安全缓冲）。
    2. 如果显存依然有大量富余，可以在引擎启动参数中尝试将 max_num_seqs 从默认的 646464 调大（如调至 128128128），观察 Decode 吐字延迟（TPOT\text{TPOT}TPOT）是否仍在可接受范围内，若不劣化则可进一步减少所需的实例数。

潜在问题 3：为什么同一个模型，按 P90 标准和按平均值（Mean）标准算出来的机器实例数差了整整一倍？​

  • 数据对比：
    • 80B80\text{B}80B：P90 需 5∼65 \sim 65∼6 个实例 vs 均值需 333 个实例；
    • 284B284\text{B}284B：P90 需 191919 个实例 vs 均值需 10∼1110 \sim 1110∼11 个实例；
    • 27B27\text{B}27B：P90 需 303030 个实例 vs 均值需 151515 个实例。
  • 原因解析：在大模型高并发压测中，当多个 3k3\text{k}3k 长输入请求在同一瞬间扎堆到达时，会产生队头阻塞（Head-of-Line Blocking）。最倒霉的那 10%10\%10% 的请求（即 P90 统计位点）必须等同批次前面的 3k3\text{k}3k 请求先做完 Prefill，导致其 TTFT\text{TTFT}TTFT 比平均值高出一大截。
  • 业务沟通建议：向业务方或客户汇报时，必须明确对齐 SLA 口径——如果业务是严苛的实时交互场景（要求 90%90\%90% 以上的请求绝对不能超过 3s3\text{s}3s），就必须按 P90 实例数 采购/分配算力；如果是后台异步批处理或对偶发延迟不敏感的内部应用，则可按 均值实例数 部署，直接节省近 50%50\%50% 的硬件成本。
